# ADR-0262 — Покупки: тихо без Telegram і одне повідомлення на кілька товарів

- **Статус:** Accepted
- **Дата:** 2026-11-10
- **Спирається на:** ADR-0033 (покупки: ввід унизу), ADR-0229 (сповіщення
  лише своїй парі)
- **Зачіпає:** нова міграція `supabase/migrations/20261110120000_shopping_notify_batch.sql`
  (`shopping_items.notify`, `batch_id`, `batch_size`), Edge Function
  `db-notify` (`index.ts`, новий `shoppingRules.ts`), `useShoppingItems.ts`
  (`shoppingInsertRows`, мутації), `ShoppingPage.tsx` (перемикач), новий
  `shoppingNotify.ts`, `shopping.css`, `shoppingWorld.css`,
  `UiIcon.tsx` (`BellIcon`, `BellOffIcon`), `PlanLinksBlock.tsx`, `types/index.ts`
- **Не зачіпає:** загальний тумблер сповіщень пари в налаштуваннях
  (`telegram_notifications_enabled` — він і далі вимикає все), бота
  (`tg-commands`), сповіщення інших модулів, парсинг вводу (`shopping-parse`)
- **Вказівка власника (2026-11-10):** «Додай можливість не надсилати
  сповіщення в телеграм в самому модулі покупок, також, якщо користувач пише в
  одному рядку багато покупок через кому, формується одне повідомлення, яке
  надсилається в телеграм списком із доданих покупок, а не по одному окремому
  повідомленні, як зараз».

## Як було

Вебхук бази на `shopping_items` (тригер `supabase_functions.http_request`)
кличе `db-notify` на КОЖЕН вставлений рядок окремо. Ввід «молоко, хліб,
яблука» вставлявся одним запитом у три рядки — і партнер отримував три
повідомлення. Вимкнути сповіщення можна було лише для всього порталу.

## Рішення

1. **Колонки** `notify boolean not null default true`, `batch_id uuid`,
   `batch_size smallint` (1…200). Типові значення лишають старі рядки, бота й
   будь-який інший клієнт такими, як були.
2. **Перемикач у модулі** — поруч із «Шаблоном», дзвоник «Telegram» /
   перекреслений «Тихо». Вимкнено — рядок пишеться з `notify = false`, і
   `db-notify` мовчить і про додане, і про «куплено» (у мить дії клієнт пише
   `notify` разом із `bought`). Вибір пам'ятає пристрій
   (`amore:shoppingNotify`); без сховища — сповіщає, як досі.
3. **Партія.** Кілька товарів одного вводу (і з плану) отримують спільний
   `batch_id` (`uuidV4` з `@/lib/entropy`) і `batch_size`. Вебхук приходить
   уже після коміту, тож кожен рядок бачить усю партію; повідомлення надсилає
   лише рядок із найбільшим id, коли видимі всі `batch_size` рядків, — одне
   повідомлення списком у порядку вводу, без дублів, хоч у якому порядку
   прийдуть виклики:

   ```
   🛒 Нові товари у списку покупок (3):
   • Молоко — 2 л
   • Хліб
   • Яблука — 1 кг
   ```

   Один товар — повідомлення як раніше.
4. **Назви екрануються** для `parse_mode: HTML` — «<» у назві більше не ламає
   повідомлення.
5. Правила (`shoppingRules.ts`) без імпортів: їх тягне функція й перевіряє
   vitest (`shoppingNotify.test.ts`), бо `deno test` у проєкті не ганяється.

## Розгортання

- Міграцію застосовано до проєкту «Amore» 2026-11-10 через Supabase MCP
  (`shopping_notify_batch`).
- `db-notify` розгорнуто через Supabase MCP (версія 22, `verify_jwt` як було);
  розгорнутий текст звірено з репозиторієм.
- Порядок безпечний: стара версія клієнта без нових полів отримує типові
  значення й поводиться як досі, поки не оновиться GitHub Pages.

## Перевірка

- Тести: партія — спільний `batch_id` і розмір, один товар без партії, тихо —
  `notify: false`; сервер — тихий мовчить, один товар — старий текст, з партії
  надсилає рівно один рядок (останній) повним списком, неповна партія —
  ніхто, тиха партія мовчить, екранування, «куплено» мовчить для тихого;
  перемикач — типово сповіщає, пам'ятає вибір, без сховища не падає.
- Живого знімка модуля немає: живий портал вимагає входу, а `.env.live` у
  пісочниці немає. Повідомлення в Telegram наживо не надсилалось.

## Ризики

- Якщо вставлення партії колись розіб'ють на кілька запитів і один впаде,
  `batch_size` рядків ніколи не стане видимим — і повідомлення не прийде
  зовсім (мовчання, а не дублі). Нинішній клієнт вставляє партію одним
  запитом.
- Перемикач — на пристрій, а не на пару: партнер на своєму телефоні має свій.
