# ADR-0207 — «Плани» стали одним питанням

- **Статус:** Accepted
- **Дата:** 2026-09-23
- **Зачіпає:** `features/plans/PlansPage.tsx`, `planFocus.ts` (новий),
  `planFocus.test.ts` (новий), `PlanFocusHero.tsx` (новий),
  `PlanIdeaDeck.tsx` (новий), `plansFocus.css` (новий),
  `plansModule.test.ts`, `app/routes.tsx`, `plans-lab.html`,
  `docs/MODULE_STATUS.md`
- **Тип зміни за `CHANGE_CONTROL_AND_ADR.md`:** переробка композиції
  модуля за вибором власника; контракти даних не змінюються
- **Вказівка власника:** «не подобається взагалі все» → три напрями в
  `plans-lab.html` → **«Варіант C, роби з нього справжній екран»**

## §1 Чому взагалі

Власник сказав про модуль: «не подобається взагалі все». Замість того щоб
вгадувати, що саме, план модуля був прочитаний із бази:

| | |
|---|---|
| 1 | активний план із датою |
| 5 | задумів без дати |
| 12 | завершених, із них **4 однакові** «Побачення, яке пам'ятаємо» |
| 1 | фото на 18 планів; 0 місць, 0 авторів, 0 посилань, 0 часу |

І звідси діагноз, який видно на знімку: **сітка місяця займала ~40%
першого вікна, щоб показати одну крапку**, розділ «Найближчі плани»
містив рівно одну картку, а справжній центр ваги — задуми без дати —
лежав нижче згину. Найбільший елемент екрана ніс найменше змісту.

## §2 Обраний напрям

Три композиції зняті в `plans-lab.html` (A — вісь часу, B — вісь стану,
C — вісь рішення), кожна з названою ЦІНОЮ, а не лише перевагою. Власник
обрав **C**.

Теза C виходить прямо з §1: п'ять із шести відкритих записів не мають
дати, отже робота екрана — не «показати список», а **перетворити задум
на план**.

Екран тепер відповідає на одне питання зверху вниз:

1. **що зараз** — один план із поступом;
2. **що наступне** — колода задумів і одна дія «Дати дату»;
3. **решта** — за тихими лічильниками.

## §3 Що знайшлось перед першим рядком коду

**`/calendar` — це редирект сюди.** Макет C календаря не показував, і
спокуса була просто прибрати сітку. Перевірка маршрутів показала, що
іншого місяця в порталі немає: `{ path: 'calendar', element: <Navigate
to="/plans" /> }`. Викинути сітку означало б забрати в пари єдиний
календар.

Тому вона не видалена, а спущена у власний лічильник, а редирект тепер
веде на `/plans?view=calendar` і розкриває її одразу — хто прийшов по
календар, бачить календар.

**Це і є різниця між макетом і екраном:** макет має право показати лише
те, про що говорить, а екран мусить лишити двері кожному запису.

## §4 Рішення, записані числом

**`focusPlan` — власний вибір, а не `nextPlan`.** Наявна `nextPlan`
відсіює все, що вже почалось (`days < 0`), бо відповідає на питання «що
попереду». «Ремонт хати» іде 84 дні — для неї його немає, а для екрана
він головний. Порядок переваги: те, що **триває** (серед кількох — те,
що скінчиться раніше), далі найближче попереду, далі нічого.

**Смуга поступу є лише там, де вона чесна.** `planProgress` мовчить про
точний день (0% чи 100% сказали б менше, ніж «через 4 дні») і про
період, який ще не почався (нерухомий нуль місяцями читається як
зламаний елемент). Для «Ремонту хати»: **84 з 549 днів**.

**Порядок колоди — продуктова думка.** `ideaQueue` кладе першим той
задум, що лежить **найдовше** (у пари це «Гончарство» від 29 липня), а
не найсвіжіший. Екран сам піднімає найзанедбаніше. Порівняння —
`byCodePoint` по `created_at` (ADR-0205), tie-break за `id`, бо чотири
записи цієї пари створені в одну секунду.

**«Дати дату» пише `date_precision: 'day'` разом зі `start_date`** — саме
ту пару, якої чекає `hasPreciseDate`. Без другого поля задум дістав би
дату й однаково лишився б поза сіткою й поза відліком, тобто дія
виглядала б зробленою й не була б.

**Нативний `input[type=date]`, а не власний календар:** той самий елемент
уже стоїть на сторінці плану, і другий спосіб вибрати дату означав би дві
поведінки на одне поле.

## §5 Названа ціна C і як вона закрита

Ціна в макеті звучала так: «список як список зникає». Зникнути він права
не має — тому три тихі лічильники (`Заплановано`, `Задуми без дати`,
`Прожито разом`) розкриваються на місці, а порожній розділ не
показується взагалі: рядок «Заплановано 0» — це шум, який ще й читається
як несправність.

На даних пари «Заплановано» справді немає: єдиний датований план — це
герой. Перевірено живим зондом.

## §6 Що виміряно

**Чиста логіка:** 18 нових перевірок у `planFocus.test.ts`, «сьогодні»
заморожене на 23 вересня 2026 — тому самому дні, на якому рахувались
числа макета. Серед них: 84 з 549; точний день не має поступу; період
завдовжки в день не ділиться на нуль; найдавніший задум стоїть першим;
`id` розводить записи, створені в ту саму мить.

**Живий портал, справжні дані** (`.audit/probe-plans.mjs`) — **16 з 16**:

```
✓ герой — «Ремонт хати»          ✓ числа: 84 дні позаду / 465 попереду
✓ у колоді перший — найдавніший   ✓ лічильник колоди «1 з 5»
✓ лічильник не накритий           ✓ порожнього «Заплановано» немає
✓ розкриття: плиток 0 → 12        ✓ aria-expanded стає true
✓ сітка місяця з'являється        ✓ /calendar → #/plans?view=calendar
✓ календар розкритий одразу       ✓ поле дати існує, нативне, назване
```

**Знімки:** телефон (темна) і широкий екран (світла).

## §7 Три вади, знайдені не типізацією

1. **Колода накривала власний лічильник.** Нижні картки мали
   `block-size: 100%`, і сотий відсоток міряв усю секцію разом із
   підписом «1 з 5» під нею. Знайшов живий знімок. Лікується власною
   обгорткою стосу плюс `inset: 0`; під це написаний сторож у
   `plansModule.test.ts`, і він перевірений поверненням вади.
2. **`.btn-primary` — класу, якого в CSS немає.** Упіймав наявний сторож
   `modalActions.test.ts`, у якого записано, що два місця вже носили цей
   клас і були неоформленими браузерними кнопками. Тут `.btn` і є
   головна дія, `.btn-ghost` — тиха.
3. **Жорсткі білий і чорний у заливках.** `rgba(255,255,255,0.03)` на
   світлому ґрунті — це ніщо, а `rgba(0,0,0,0.34)` дало б доріжку,
   темнішу за текст. Показала світла тема на широкому екрані; обидва
   переведені на `color-mix` від `--text`.

## §8 Названі межі

1. **Запис у базу не перевірявся на живих даних.** «Дати дату» — єдина
   дія екрана, що пише, і виконати її означало б поставити дату
   справжньому задуму пари. Без слова власника я цього не робив.
   Перевірено все, крім самого запису: поле існує, нативне, назване для
   озвучення, кнопка його відкриває; патч покритий типами й описаний у
   §4. **Першу справжню дату поставить власник.**
2. **`confirmed` свідомо не питається.** У базі всі 18 планів
   підтверджені, а `proposed_by` не заповнений жодного разу — тобто
   розрізнення «пропозиція проти спільного плану» сьогодні не несе
   інформації. Кнопка «Підтвердити» лишається в списках під
   лічильниками, тож непідтверджений план нікуди не зникає.
3. **Чотири дублікати «Побачення, яке пам'ятаємо» не зведені.** Варіант
   B пропонував це прямо в інтерфейсі; C їх лише не приховує — вони
   лежать у «Прожито разом». Зведення — це запис у дані пари, тобто
   окреме рішення власника.
4. **Старі стилі модуля не прибрані.** `plansOverview.css` і сусіди
   лишаються: під ними живуть `PlanTile`, сторінка плану й модалки.
   Прибирання мертвих правил — окрема робота з власним заміром, і
   робити її «заразом» означало б змішати дві зміни в одну.
5. **E2E у модуля як не було, так і немає.** Перевірка вище — зонд, який
   ганяється руками, а не крок CI. Риф свою спеку дістав (ADR-0204);
   «Плани» лишаються без неї.
