# Жива перевірка порталу

Одна команда замість «підняти сервер → залогінитись → дочекатись сцени →
зняти екран», яку доводилось збирати заново щоразу.

```bash
npm run live -- wishlist --probe=.wl-sphere
npm run live -- home wishlist --device=phone,wide
npm run live -- wishlist --tap=.wl-sphere --tier=low
npm run live -- --help
```

Знімки лягають у `.live/` (у `.gitignore`), а в консоль іде те, що інакше
довелось би міряти руками: якість профілю, кількість тіл, draw calls,
трикутники, координати елементів і помилки сторінки.

## Навіщо це існує

Кожну справжню ваду в цьому проєкті знайшов живий екран, а не типізація й не
тести. Тести тримають інваріанти; вони не бачать, що тіло вийшло за кадр, що
фото не доїхало, що дотик не доходить до елемента або що сторінка забрала
подію собі.

Але живий екран легко бреше. Нижче — шість способів, якими він брехав саме
тут, і кожен уже коштував хибного висновку. Перші п'ять закриті в
`portal.mjs`, і саме тому цей скрипт варто запускати замість власного;
шостий закрити неможливо, його треба знати:

1. **Service worker.** PWA кешує збірку, і сторінка показує вчорашній код на
   свіжому сервері. Двічі поспіль перевірку «виправлено» було зроблено на
   старому файлі. Тому `serviceWorkers: 'block'`.
2. **CORS для текстур і взагалі вихід назовні.** Supabase, Cloudinary, тайли
   карти (`tiles.openfreemap.org`) і геокодер (`nominatim.openstreetmap.org`)
   ідуть реле через Node, і до відповіді **обов'язково** додається
   `access-control-allow-origin: *`. Без нього WebGL мовчки відмовляється
   брати текстуру: мережа каже «200», а фото на камені немає.

   **Кожен новий зовнішній постачальник треба дописати в `RELAY_HOSTS`.** У
   пісочниці браузер не має прямого виходу назовні: сторонній домен віддає
   `TypeError: Failed to fetch`, і це не схоже на помилку — просто екран
   лишається порожнім. Карта спогадів упіймалась саме так: полотно
   створилось, WebGL завівся, а запиту до тайлів не пішло жодного.
3. **WebGL.** У безголовому Chromium він працює лише зі SwiftShader
   (`--enable-unsafe-swiftshader --use-angle=swiftshader-webgl`).
4. **Профіль пристрою.** Якість сцени вибирається з `navigator.deviceMemory` і
   `hardwareConcurrency`. Безголовий браузер повідомляє власні числа, тож без
   підміни перевіряється завжди одна гілка. `--tier=high|balanced|low`.
5. **Час.** Спершу ознака, потім час: скрипт чекає
   `data-evolution-preview="ready"`, тоді `data-evolution-runtime="ready"`,
   тоді завантаження всіх зображень — і лише потім `--settle` на приїзд камери
   (ADR-0022). Знімок без цього показує кадр, якого користувач не бачить.
6. **Швидкість часу.** Сцена малюється програмно (SwiftShader), тож кадри тут
   ідуть **по три на секунду** — виміряно, 175 кадрів за 55 секунд на
   `#/wishlist`. Знімка це не стосується, але будь-яка перевірка тривалості
   бреше вдвадцятеро: анімація, яка на телефоні триває три секунди, тут займе
   майже хвилину. Одна вада вже пройшла повз саме так — повернення куль
   рахувало час обрізаним кроком фізики і на рідких кадрах не наставало
   зовсім (ADR-0028). Міряй прогрес, а не «встигло за N секунд».

## Порівняння знімків

```bash
npm run live -- home --still --out=.live/before
# …зміни…
npm run live -- home --still --out=.live/after
npm run live:diff -- .live/before/home-phone-still.png .live/after/home-phone-still.png --ignore=0,0,824,300
```

Два числа, які варто знати перед першим порівнянням — обидва виміряні:

- **Без `--still` два запуски того самого коду розходяться на 10.5% пікселів.**
  Камінь дихає, іскри мерехтять, камера дрейфує. На такому шумі питання «чи
  щось змінилось» відповіді не має.
- **Із `--still` — 0.46%, і всі до одного в смузі 406×40 угорі кадру.** Це
  рядок привітання на головній: він випадковий із набору. Виключиш його
  (`--ignore=0,0,824,300` для `phone@2`) — залишається **нуль пікселів**.

Тобто заморожена сцена відтворюється до біта, і різниця, яку показує `diff`,
є справжньою зміною, а не шумом. Третім файлом можна дати ще один знімок тієї
самої збірки — тоді скрипт сам скаже, вища різниця за шум чи ні.

`--still` вмикає `prefers-reduced-motion`, який портал уже поважає; знімок
отримує суфікс `-still`, щоб живий і застиглий кадри не ділили одне ім'я.

## Облікові дані

Ті самі змінні, що й у приймальному тесті:

```
VISUAL_USER_NAME=…
VISUAL_USER_PIN=…
```

У середовищі або у файлі `.env.live` в корені (він у `.gitignore` — у git не
потрапляє).

## Приймальний набір локально

`npm run live` показує; `npx playwright test` стверджує й падає в CI. Другий
довго не можна було ганяти локально взагалі — сторінка в пісочниці не дістає
до Supabase, і всі 23 тести падали на «waiting for button Діма», тобто на
логіні. Причину кожного справжнього падіння доводилось читати в логах CI по
п'ятнадцять хвилин на спробу.

Тепер локальний прогін можливий: preview-сервер віддає Supabase через власний
проксі, а браузер береться готовий з образу.

```bash
SB=$(grep -m1 VITE_SUPABASE_URL .env.local | cut -d= -f2-)

# 1. Збірка, у якій адреса Supabase вказує на проксі preview-сервера.
LOCAL_SUPABASE_PROXY="$SB" VITE_SUPABASE_URL="http://127.0.0.1:4173/__supabase" npm run build

# 2. Сервер із тим проксі (Playwright підхопить уже запущений).
LOCAL_SUPABASE_PROXY="$SB" npx vite preview --host 127.0.0.1 --port 4173 &

# 3. Набір або окремий файл.
VISUAL_USER_NAME=… VISUAL_USER_PIN=… \
PLAYWRIGHT_CHROMIUM=/opt/pw-browsers/chromium-1194/chrome-linux/chrome \
npx playwright test e2e/visual/wishlist.visual.spec.ts
```

Три речі, які варто знати:

- **Збірку з таким `VITE_SUPABASE_URL` не можна публікувати** — адреса в ній
  локальна. Деплой збирається окремим кроком у CI зі справжніми змінними, тож
  переплутати їх ніде, але переписати `dist` перед ручним завантаженням —
  можна.
- **Playwright перевикористовує вже запущений сервер.** Якщо той піднявся без
  `LOCAL_SUPABASE_PROXY`, набір знову впаде на логіні: сервер треба
  перезапустити, а не набір.
- **Програмний рендерер тут повільніший за CI.** Дерево під ним подеколи не
  вкладається в `maxBuildMs`, і приймальний статус стає `fail build-ms`. Це
  властивість пісочниці, а не порталу — на раннері той самий тест проходить.

## Що це не робить

- **Не замінює приймальний тест.** `e2e/visual/` перевіряє бюджети й падає в
  CI; цей скрипт нічого не стверджує — він показує. Різні задачі.
- **Не дає еталонів.** Порівняння тут ручне, файл проти файлу. Еталони в CI —
  наступний крок, і `--still` існує саме для того, щоб він став можливим.
- **Не перевіряє реальний телефон.** SwiftShader малює не так, як GPU Pixel 8
  Pro, і продуктивність тут не міряється взагалі.
