# Жива перевірка порталу

Одна команда замість «підняти сервер → залогінитись → дочекатись сцени →
зняти екран», яку доводилось збирати заново щоразу.

```bash
npm run live -- wishlist --probe=.wl-sphere
npm run live -- home wishlist --device=phone,wide
npm run live -- wishlist --tap=.wl-sphere --tier=low
npm run live -- --help
```

Знімки лягають у `.live/` (у `.gitignore`), а в консоль іде те, що інакше
довелось би міряти руками: якість профілю, кількість тіл, draw calls,
трикутники, координати елементів і помилки сторінки.

## Навіщо це існує

Кожну справжню ваду в цьому проєкті знайшов живий екран, а не типізація й не
тести. Тести тримають інваріанти; вони не бачать, що тіло вийшло за кадр, що
фото не доїхало, що дотик не доходить до елемента або що сторінка забрала
подію собі.

Але живий екран легко бреше. Нижче — тринадцять способів, якими він брехав саме
тут, і кожен уже коштував хибного висновку. Перші шість закриті в
`portal.mjs`, і саме тому цей скрипт варто запускати замість власного;
дев'ятий закритий у переході між маршрутами; решту закрити неможливо, їх
треба знати:

1. **Service worker.** PWA кешує збірку, і сторінка показує вчорашній код на
   свіжому сервері. Двічі поспіль перевірку «виправлено» було зроблено на
   старому файлі. Тому `serviceWorkers: 'block'`.
2. **CORS для текстур і взагалі вихід назовні.** Supabase, Cloudinary, тайли
   карти (`tiles.openfreemap.org`), геокодер (`nominatim.openstreetmap.org`)
   і TMDB разом із її постерами (`api.themoviedb.org`, `image.tmdb.org`)
   ідуть реле через Node, і до відповіді **обов'язково** додається
   `access-control-allow-origin: *`. Без нього WebGL мовчки відмовляється
   брати текстуру: мережа каже «200», а фото на камені немає.

   **Кожен новий зовнішній постачальник треба дописати в `RELAY_HOSTS`.** У
   пісочниці браузер не має прямого виходу назовні: сторонній домен віддає
   `TypeError: Failed to fetch`, і це не схоже на помилку — просто екран
   лишається порожнім. Карта спогадів упіймалась саме так: полотно
   створилось, WebGL завівся, а запиту до тайлів не пішло жодного.
3. **WebGL.** У безголовому Chromium він працює лише зі SwiftShader
   (`--enable-unsafe-swiftshader --use-angle=swiftshader-webgl`).
4. **Профіль пристрою.** Якість сцени вибирається з `navigator.deviceMemory` і
   `hardwareConcurrency`. Безголовий браузер повідомляє власні числа, тож без
   підміни перевіряється завжди одна гілка. `--tier=high|balanced|low`.
5. **Час.** Спершу ознака, потім час: скрипт чекає
   `data-evolution-preview="ready"`, тоді `data-evolution-runtime="ready"`,
   тоді завантаження всіх зображень — і лише потім `--settle` на приїзд камери
   (ADR-0022). Знімок без цього показує кадр, якого користувач не бачить.
6. **Девтули React Query поверх дока.** Кнопка `.tsqd-open-btn` живе лише в
   dev-збірці — пара її не побачить, — але харнес знімає саме dev-сервер, і
   вона накриває правий край дока. Виміряно `elementsFromPoint(376, 875)`:
   найвищим елементом у точці кнопки «Ще» був девтул, а не пункт навігації.
   Тому `--tap` по «Ще» **звітував про успіх** і меню не відкривав — клік
   з'їдала чужа кнопка. Ховається стилем у `portal.mjs`; щоб девтули
   знадобились, є `--headed`.
7. **Швидкість часу.** Сцена малюється програмно (SwiftShader), тож кадри тут
   ідуть **по три на секунду** — виміряно, 175 кадрів за 55 секунд на
   `#/wishlist`. Знімка це не стосується, але будь-яка перевірка тривалості
   бреше вдвадцятеро: анімація, яка на телефоні триває три секунди, тут займе
   майже хвилину. Одна вада вже пройшла повз саме так — повернення куль
   рахувало час обрізаним кроком фізики і на рідких кадрах не наставало
   зовсім (ADR-0028). Міряй прогрес, а не «встигло за N секунд».

8. **Втрата WebGL-контексту на знімку.** Найважча сцена порталу — риф —
   подеколи втрачає контекст саме в мить `page.screenshot()`: у логах
   поруч стоять `GPU stall due to ReadPixels` і `THREE.WebGLRenderer:
   Context Lost`. PNG при цьому виходить не порожній і не зламаний на
   вигляд — він показує ґрунт сторінки з білою плямою там, де мала бути
   сцена. Тобто **виглядає як зламана тема, а не як збій рендерера**.

   Це вже коштувало хибного висновку: чотири знімки поспіль показали
   білий риф одразу після зміни токенів, два попередні знімки до неї були
   цілі — і зміна виглядала винною поза сумнівом. Насправді з ВИМКНЕНОЮ
   зміною риф був так само білий, а той самий портал без `screenshot()`
   не втрачав контексту жодного разу з трьох.

   Мораль: **перш ніж звинуватити свою зміну, зніми той самий кадр із
   вимкненою зміною — у ТОМУ Ж прогоні, а не годину тому.** Порядок
   знімків у часі не є доказом причини; пісочниця деградує впродовж
   сесії. Якщо в консолі є `Context Lost`, знімок сцени не є свідченням ні
   про що.

9. **Маршрут із запитом мовчки втрачав запит.** Перехід між маршрутами робив
   рівно одне: `window.location.hash = …`. Для `#/plans` це правда — портал
   маршрутизується хешем. Для `/?treeLod=low` це брехня: рядок запиту в хеш не
   потрапляє, сторінка лишається з тим `location.search`, з яким завантажилась
   (тобто порожнім), і знімок показує **зовсім іншу гілку, ніж просили**.

   Коштувало це хибного висновку рівно один раз, і висновок був гучний: три
   прогони з `?treeLod=low|medium|high` дали три ОДНАКОВІ розклади сцени, і з
   цього мало не народилось «прапорець LOD у дерева мертвий, пара завжди
   отримує одну й ту саму сітку». Насправді мертвим був перехід. У рушії LOD
   міняє сітку стовбура втричі — 2 328 / 7 553 / 9 474 трикутники.

   Закрито: маршрут із `?` тепер перезавантажує сторінку повністю. Сесія живе
   в `localStorage`, тож логін це переживає.

   Мораль: **три однакові числа — це не доказ, що ручка не працює. Спершу
   перевір, що ручку взагалі повернули.**

10. **Мірка граней хитається від камери сильніше, ніж від кристала.**
    `scripts/lab/artifact.mjs` бере СТАЛУ смугу пікселів (`--band`, типово
    900–1100) і рахує медіану стрибків яскравості на межах граней. Смуга
    стала, а кадр — ні: він масштабується коробкою ВСІХ мешів сцени, тож
    будь-яка зміна підкладки посуває камеру, і смуга починає перетинати
    інше місце тіла.

    Виміряно на одному й тому самому кристалі, `--years=11 --theme=dark`,
    самою лише ручкою відстані:

    | камера | медіана меж |
    |---|---|
    | 1.00 | 23% |
    | 1.05 | **42%** |
    | 1.10 | 32% |
    | 1.15 | 35% |

    Тобто п'ять відсотків ходу камери міняють число вдвічі. Це вже
    коштувало хибного висновку: після того, як насип підкладки став
    вужчим (ADR-0156), камера під'їхала, число впало з 48% до 24%, і з
    цього мало не народилось «кристал перестав читатись кристалом».
    Кристал не змінився жодним трикутником.

    Мораль: **порівнювати ці числа можна тільки при однаковому кадрі.**
    Для цього в `artifact.mjs` є `--cam`, а в лабораторії `?cam=` і
    `?eye=`. Якщо зміна чіпає габарит будь-чого в сцені — міряй обидва
    стани при `--cam`, підібраному так, щоб артефакт займав однакову
    частку кадру, або не роби висновку взагалі.

11. **Знімки порталу — RGB, а не RGBA, і власна мірка, що пише крок 4, читає
    зсунуті байти.** `decodePng` повертає `channels` разом із `data` саме
    тому: тип PNG тут 2 (три канали), тож `(y * width + x) * 4` попадає в
    піксель, зсув якого росте вздовж рядка. Кожне число, зняте такою міркою,
    — випадкове.

    Це не гіпотеза. Одноразовим скриптом із кроком 4 у цьому проєкті було
    отримано «розрив дальніх хмар із небом 99 з 255 проти 26 у ближніх» і
    «88 з 255 там, де хмар немає зовсім»; правильним кроком ті самі кадри
    дають **58.6 проти 44.9**, а на кадрі без хмар — нуль. Перше число
    встигло потрапити в ADR і `MODULE_STATUS.md`, звідки й було виправлене
    (ADR-0165 §6).

    Найгірше в цій ваді те, що вона дає ПРАВДОПОДІБНІ числа: байти беруться
    з тієї самої картинки, тож порядок величини лишається схожим, і ніщо в
    результаті не кричить «я зламане».

12. **Смуга без маски міряє острів, а не кристал, і плато не є гранню.**
    Пункт 10 казав, що мірку граней «не можна порівнювати між змінами». Це
    було надто м'яко: вона не міряла кристал узагалі (ADR-0174).

    Три вади разом. Смуга 900–1100 на теперішньому кадрі проходить НИЖЧЕ
    стовбура монарха — по дітках і по щебеню жеоди. Стовпець усереднював усю
    висоту смуги, тобто небо над тілом і мох під ним разом із каменем. А
    `findPlateaus` шукає пробіг, рівний у межах 8%, — і грань ним не є: у неї
    власний перепад ~20% (ADR-0085), а по тілу розсипані іскри, кожна з яких
    робить стовпець на 17–32% яскравішим за сусідні.

    Числа: із двадцяти трьох плато в тій смузі кристалові належали **два**;
    три різні терми (`skyStrength`, `glassStrength`, `rimStrength`) давали
    результат ЧИСЛО В ЧИСЛО однаковий, бо жоден із них не міняв нічого там,
    куди дивився прилад; а на самому стовбурі прилад знаходив **нуль** плато
    там, де око бачить шість граней із кроками 33–43%.

    Закрито в `artifact.mjs`: тіло знаходиться маскою, смуга береться від
    тіла, грань шукається від ребра (`findFacets`), яскравість грані —
    медіана. Але `shot.mjs` і `photoProfile.mjs` досі рахують плато по
    всьому кадру: там та сама вада відкрита.

13. **Два знімки підряд — це два різні кадри.** `artifact.mjs` знімав один
    кадр у файл і другий у вимір. Сцена жива — іскри мерехтять, кадр життя
    дихає, — тож звіт описував кадр, якого немає у файлі: «5 граней,
    найслабша пара 24%» проти шести граней і 32% у збереженому знімку.
    Перевірити звіт по файлу було неможливо, і саме цим вада й небезпечна:
    вона не ламає числа, вона розриває їх із доказом.

    Закрито наскільки можна: `luminance.mjs` експортує `pixelAt(image, x, y)`,
    і в одноразових мірках треба брати піксель ним, а не арифметикою.
    Хардкоду кроку в самому наборі більше немає.

    Мораль: **перш ніж вірити числу, перевір, що мірка читає той піксель,
    який показує кадр.** Найдешевша перевірка — зняти три пікселі з місць,
    колір яких відомий наперед (небо, порода, артефакт), і глянути на них
    очима.

## Зум сцени рукою

```bash
npm run live -- home --still --zoom=-8 --zoom=8
```

`--zoom=<клацань>` крутить колесо над полотном: від'ємне — ближче, додатне —
далі. Прапорців може бути кілька, і вони йдуть ПОСЛІДОВНО від того місця, де
камера вже стоїть, — інакше не поставити питання «а чи вертається назад».

Поруч друкується **розмір артефакта в пікселях** і його відношення до першого
кадру, і це головне тут. Знімок після зуму виглядає правдоподібно навіть тоді,
коли камера не зрушила: сцена жива, кадр щоразу трохи інший, і око читає цю
різницю як «подіяло». Виміряно з `--still`, ADR-0160:

| жест | висота артефакта | до першого кадру |
|---|---|---|
| — | 898 px | ×1.00 |
| ближче 8 | 1207 px | ×1.34 |
| далі 8 | 898 px | ×1.00 |
| далі 8 | 636 px | ×0.71 |
| ближче 8 | 898 px | ×1.00 |

Дві межі оснастки, які варто знати (обидві вже коштували хибного висновку —
див. ADR-0160 §8):

1. **Колесо, а не щипок.** CDP уміє послати `wheel` і не вміє двопальцевий
   `TouchEvent` без ручної збірки. Обидва входи `OrbitControls` ведуть в один
   `dollyIn/dollyOut`, тож колесо перевіряє ту саму дорогу — але воно **не
   доводить**, що щипок доходить до полотна на телефоні.
2. **Артефакт міряється НАЙБІЛЬШОЮ ЗВ'ЯЗНОЮ ПЛЯМОЮ свого відтінку**
   (`artifactSpan.mjs`), бо полотно порталу займає весь екран і обмежити
   пошук ним неможливо. Рожеве емодзі у привітанні вже піднімало «висоту
   артефакта» з 754 до 1292. І в другий бік: коли артефакт більший за екран,
   мірка впирається у висоту кадру — «×5 ближче» вона підтвердити не може,
   вона підтверджує лише, що жест зупинився.

## Розклад сцени по об'єктах

```bash
npm run live -- home --breakdown --seed=amore:home-artifact=tree
```

`gl.info.render.triangles` каже, СКІЛЬКИ трикутників намальовано, і не каже
ЧИМ. Бюджетна робота питає саме друге, і без відповіді вона ворожить: гіпотеза
«листя, терен і трава — головні витрати дерева» обіцяла −40%, дала −5%, бо всі
троє разом важили менше за четвертого, якого ніхто не зважував.

`--breakdown` обходить сцену й друкує кожен об'єкт із його вагою і часткою.
Саме він показав, що **тло коштує дорожче за дерево**: небо, пагорби, сонце й
терен разом давали 11 000 трикутників із 36 572, тобто 30% кадру на те, що
телефон показує кількома десятками пікселів.

Читає `window.__amoreEvolutionScene` — ручку, яку сцена кладе **лише в
dev-збірці**. У продакшні її немає, і команда чесно скаже про це замість того,
щоб вигадати число.

## Профіль світла: чи справді грані різняться

```bash
npm run live -- home --profile=1000-1080,230-590
```

Правило `amore-crystal-look` одне: **міряй, перш ніж крутити**. Кристал, який
читається кристалом, має сусідні грані, що різняться на 30%+; нижче ~10% він
виглядатиме гладкою формою, хай яким правильним буде решта. Досі цю перевірку
робили руками — зняти екран, вирізати тіло, пройти смугою пікселів,
розкодувати криву, знайти плато, — тобто година на питання, на яке має
відповідати одна команда.

`--profile=y0-y1[,x0-x1]` бере смугу знімка, знімає гамму sRGB, **обертає
криву тонування** й друкує плато яскравості та відсотки між сусідніми.

Три речі, які тут зроблено навмисно:

1. **Крива читається зі сцени, а не припускається.** R3F ставить ACES за
   замовчуванням, але `flat` на полотні це вимикає — і профіль, який обернув
   би криву даремно, звітував би про світло, якого немає.
2. **Знімок — це не вимір світла.** Крива стискає різниці, і тим сильніше, чим
   яскравіші відліки: байти 230→245 різняться на екрані на 13.3%, а в сцені —
   на **52.1%**. Саме тому спершу обертається крива, і лише тоді щось
   порівнюється.
3. **Крайні плато відкидаються.** Перехід тіло↔тло — це силует, а не грань;
   він завжди вісімдесят із гаком відсотків і, якби лишався, ховав би
   справжнє число за собою.

Плато тут — пробіг стовпців, рівний ЦІЛКОМ, а не «сусіди, схожі між собою».
Перша редакція групувала сусідів і різала плавний градієнт на десяток
фальшивих плато, звітуючи про грані там, де була одна гладка поверхня.

## Екран входу

```bash
npm run live -- login --no-login --settle=800
```

Скрипт САМ проходить логін, тож без цього прапорця екран входу зняти
неможливо — і саме тому він єдиний лишався поза оглядом за всю історію
проєкту. Коли його нарешті знято, виявилось, що імена пари на ньому
фактично невидимі: біла картка зі старої рожевої ери, а чорнило з токена
темної теми, тобто **1.24:1** там, де треба 4.5 (ADR-0047).

Мораль ширша за один екран: **те, чого оснастка не знімає, не перевіряє
ніхто.**

## Колір — числом

```bash
npm run live -- wishlist --theme=light --ink=.wl-archive-add-gift
#   колір   .wl-archive-add-gift: #8d5264 (відтінок 342°) на #f5dfe4, контраст 4.71:1
```

`--probe` міряє геометрію; поки колір міряти не було чим, кожне
твердження про тему лишалось здогадом. Ту саму кнопку я на знімку назвав
і рожевою, і фіолетовою — правильною виявилась перша здогадка, але
дізнатись це можна було тільки числом (ADR-0056).

Проба працює і після `--tap`, бо те, що треба зважити, здебільшого
з'являється саме там: архів, модалка, аркуш.

Дві речі, які варто знати:

- **Тло — перше НЕПРОЗОРЕ вгору по предках.** Над 3D-небом це тло
  сторінки, а не піксель неба: для тексту поверх сцени контраст буде
  оптимістичним. Такий текст досі треба міряти проти кольору неба руками.
- **Невідома форма кольору каже, що вона невідома.** Chromium повертає
  `color-mix` як `color(srgb r g b)` з каналами 0…1; його проба розбирає.
  Все інше друкується як «не розібрано» — раніше перша редакція мовчки
  вигрібала «82» з відсотка й звітувала майже чорне чорнило.

## Фото-еталон проти нашого кадру

Власник надсилає знімок і каже «зроби так». З такого знімка досі виходила
лише проза — «глибший», «оптичніший», — а з прози не буває ані числа, ані
засувки.

```bash
node scripts/live/photoProfile.mjs <фото.jpg> .live/crystal-lab-11y-high-dark-base.png \
  --a=292,378,120,395 --b=345,455,730,1180
```

Знімає з обох чотири величини: відтінок і насиченість (чи це той самий
камінь), розмах яскравості (чи він оптичний — прозорий кристал темний у
товщі й світлий на ребрах), підйом від підніжжя до вістря (куди в ньому
збирається світло) і контраст граней тими ж `findPlateaus`/
`facetSeparations`, що й профіль світла.

**Контраст граней тут читається з пункту 12 як застереження, а не як число
для порівняння з лабораторією.** `findPlateaus` не бачить грані з власним
перепадом і з іскрами; вердикт «читається кристалом» дає `artifact.mjs`
через `findFacets`. Тут ці функції лишились тому, що фото-еталон — інший
кадр із іншим тілом, і переносити на нього маску кристала без окремого
виміру означало б повторити ту саму помилку в другий бік.

**Вікно задається руками, і це навмисне.** Автоматична маска «пікселі
насиченіші за поріг» тут уже збрехала: щойно тіло темнішало, маска брала
інші пікселі, і вимір мінявся разом із тим, що міряв.

## Порівняння знімків

```bash
npm run live -- home --still --out=.live/before
# …зміни…
npm run live -- home --still --out=.live/after
npm run live:diff -- .live/before/home-phone-still.png .live/after/home-phone-still.png --ignore=0,0,824,300
```

Два числа, які варто знати перед першим порівнянням — обидва виміряні:

- **Без `--still` два запуски того самого коду розходяться на 10.5% пікселів.**
  Камінь дихає, іскри мерехтять, камера дрейфує. На такому шумі питання «чи
  щось змінилось» відповіді не має.
- **Із `--still` — 0.46%, і всі до одного в смузі 406×40 угорі кадру.** Це
  рядок привітання на головній: він випадковий із набору. Виключиш його
  (`--ignore=0,0,824,300` для `phone@2`) — залишається **нуль пікселів**.

Тобто заморожена сцена відтворюється до біта, і різниця, яку показує `diff`,
є справжньою зміною, а не шумом. Третім файлом можна дати ще один знімок тієї
самої збірки — тоді скрипт сам скаже, вища різниця за шум чи ні.

`--still` вмикає `prefers-reduced-motion`, який портал уже поважає; знімок
отримує суфікс `-still`, щоб живий і застиглий кадри не ділили одне ім'я.

## Облікові дані й адреса Supabase

Чотири змінні, і всі чотири читаються **або з середовища, або з файла**:

```
VITE_SUPABASE_URL=https://<проєкт>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon>
VISUAL_USER_NAME=…
VISUAL_USER_PIN=…
```

Перші дві бере Vite (`.env.local`), другі дві — оснастка (`.env.live`). Обидва
файли в `.gitignore`.

### Вхід без PIN

PIN зберігається як `sha256` (`users.pin_hash`), тож із бази його не дістати.
Але пароль у Supabase Auth — це і **є** той самий хеш: `auth-pin` звіряє PIN і
віддає клієнтові `{ email, password: pin_hash }`. Отже той, хто має службовий
доступ до бази, може увійти, не знаючи PIN:

```
VISUAL_USER_NAME=Діма
VISUAL_USER_EMAIL=dima@portal.app
VISUAL_USER_PIN_HASH=<64 hex із users.pin_hash>
```

Оснастка тоді бере сесію чесним `/auth/v1/token`, кладе її в `localStorage`
під ключем `amore-auth` (клієнт задає СВІЙ ключ, не типовий) разом із
`portal_session_user_id` — і застосунок прокидається вже всередині порталу.

Що це коштує, названо вголос: рядок у `.env.live` дорівнює паролю. Він
відмикає рівно те саме, що й вхід через екран (RLS однакова), і живе стільки,
скільки контейнер. Якщо ключ сховища в `src/lib/supabase.ts` колись зміниться,
оснастка НЕ зніме екран входу мовчки — вона впаде з поясненням. **У пісочниці Claude Code краще класти всі чотири в
змінні середовища самої пісочниці**: файли живуть, доки живе контейнер, а
змінні переживають перезапуск, і тоді жива перевірка доступна з першої
хвилини сесії, без жодного налаштування.

### «Пісочниця не дістає до Supabase» — це було неправдою

Кілька сесій поспіль звіти казали, що `npm run live` у пісочниці неможливий,
бо Supabase звідси недосяжний. Перевірено 2026-09-07:

```
curl https://supabase.com/                       200
curl https://api.supabase.com/                   404   ← відповів сам Supabase
curl -H "apikey: <anon>" https://<проєкт>.supabase.co/auth/v1/health   200
```

Політика виходу назовні Supabase **не блокує**. Недосяжною була заглушка:
у `.env.local` пісочниці стояло `https://sandbox.invalid` — адреса, яку туди
поставили рівно для того, щоб клієнт Supabase сконструювався й лабораторії не
падали до першого кадру. Ніхто потім не перевірив, чи це ще й обмеження
мережі, і «недосяжно» шість разів переїхало зі звіту у звіт.

**Мораль, ширша за цей файл:** заглушка, поставлена, щоб щось не падало, за
тиждень стає «фактом про середовище». Перевіряти треба сам факт, а не свою
пам'ять про нього.

Зі справжньою адресою екран входу малюється з живими іменами з таблиці
`users` — тобто ланцюг «пісочниця → браузер → реле в `portal.mjs` → Supabase»
працює цілком:

```bash
node scripts/live/shot.mjs login --no-login
```

Це найдешевша перевірка зв'язку: якщо на кнопках справжні імена, мережа є, і
далі лишається тільки PIN.

## Приймальний набір локально

`npm run live` показує; `npx playwright test` стверджує й падає в CI. Другий
довго не можна було ганяти локально взагалі — сторінка в пісочниці не дістає
до Supabase, і всі 23 тести падали на «waiting for button Діма», тобто на
логіні. Причину кожного справжнього падіння доводилось читати в логах CI по
п'ятнадцять хвилин на спробу.

Тепер локальний прогін можливий: preview-сервер віддає Supabase через власний
проксі, а браузер береться готовий з образу. (Причина, названа вище, була
поставлена неточно: сторінка не діставала до Supabase не через політику
мережі, а через заглушку в `.env.local`. Проксі preview-сервера все одно
потрібен — Playwright піднімає сторінку без реле з `portal.mjs`.)

```bash
SB=$(grep -m1 VITE_SUPABASE_URL .env.local | cut -d= -f2-)

# 1. Збірка, у якій адреса Supabase вказує на проксі preview-сервера.
LOCAL_SUPABASE_PROXY="$SB" VITE_SUPABASE_URL="http://127.0.0.1:4173/__supabase" npm run build

# 2. Сервер із тим проксі (Playwright підхопить уже запущений).
LOCAL_SUPABASE_PROXY="$SB" npx vite preview --host 127.0.0.1 --port 4173 &

# 3. Набір або окремий файл.
VISUAL_USER_NAME=… VISUAL_USER_PIN=… \
PLAYWRIGHT_CHROMIUM=/opt/pw-browsers/chromium-1194/chrome-linux/chrome \
npx playwright test e2e/visual/wishlist.visual.spec.ts
```

Три речі, які варто знати:

- **Збірку з таким `VITE_SUPABASE_URL` не можна публікувати** — адреса в ній
  локальна. Деплой збирається окремим кроком у CI зі справжніми змінними, тож
  переплутати їх ніде, але переписати `dist` перед ручним завантаженням —
  можна.
- **Playwright перевикористовує вже запущений сервер.** Якщо той піднявся без
  `LOCAL_SUPABASE_PROXY`, набір знову впаде на логіні: сервер треба
  перезапустити, а не набір.
- **Програмний рендерер тут повільніший за CI.** Дерево під ним подеколи не
  вкладається в `maxBuildMs`, і приймальний статус стає `fail build-ms`. Це
  властивість пісочниці, а не порталу — на раннері той самий тест проходить.

## Що це не робить

- **Не замінює приймальний тест.** `e2e/visual/` перевіряє бюджети й падає в
  CI; цей скрипт нічого не стверджує — він показує. Різні задачі.
- **Не дає еталонів.** Порівняння тут ручне, файл проти файлу. Еталони в CI —
  наступний крок, і `--still` існує саме для того, щоб він став можливим.
- **Не перевіряє реальний телефон.** SwiftShader малює не так, як GPU Pixel 8
  Pro, і продуктивність тут не міряється взагалі.
